# Calendars of interest

:::::panel

:::: left
A **calendar of interest** is a shared, read-only calendar that an organization defines once and then attaches to many [users](/reference/users/): typically public holidays, company closing days, school holidays, trade-show weeks or any other set of dates that matter to a whole population. It is not connected to an external provider: its content is generated by Vyte from **rules**.

- A calendar of interest contains one or more **sub-calendars of interest** (for example "National holidays" and "Regional holidays"), so that each user can pick the subset that applies to them.
- A **rule** describes one recurring or one-off date in business terms ("December 25 every year", "the 4th Thursday of November", "the last Monday of May", "August 3 to August 14, 2026") and is attached to one or more sub-calendars of the calendar. Vyte turns each rule into concrete calendar entries (its **occurrences**), generated in the background for the coming years.
- Once a calendar of interest is **added to** a user (individually, by team, or for the whole organization), it appears in that user's [calendar list](/reference/calendars/) as a calendar whose `source` is `vyte_calendar_of_interest`, with one sub-calendar per sub-calendar of interest. Each of these sub-calendars has the usual `display` and `busy` flags: with `busy: true` the generated entries make the user unavailable for bookings (for example nobody can book the user on a public holiday); with `display: true` they are shown in the user's calendar.

Authentication, key scopes, error format, dates and timezones are described in [Conventions](/reference/).

## The Calendar of interest object

| Field | Type | Writable | Description |
| --- | --- | --- | --- |
| `_id` | string (id) | no | Id of the calendar of interest. |
| `name` | string | yes | Name of the calendar, shown to users in their calendar list. HTML is sanitized. Required at creation. |
| `org` | string (id) | no | Id of the organization that owns the calendar. Set from the API key at creation. Only the owner organization can modify or delete the calendar. |
| `public` | boolean | no | Default `false`. `true` for calendars that Vyte makes available to every organization (shared catalog, for example national holidays). A public calendar that your organization does not own is listed and can be added to your users, but cannot be modified. |
| `subcalendar_of_interests[]` | array of Sub-calendar of interest (or of ids) | yes | Sub-calendars of the calendar. Returned as full objects by the list, create and update endpoints, and as ids (strings) by the `add_to` endpoints. |
| `cal_event_rules[]` | array of Rule | no | Rules attached to any sub-calendar of this calendar. Returned **only by the list endpoint**. Managed with the rule endpoints. |
| `createdAt` | string (ISO 8601 date) | no | Creation date. |
| `updatedAt` | string (ISO 8601 date) | no | Last modification date. |

### The Sub-calendar of interest object

| Field | Type | Writable | Description |
| --- | --- | --- | --- |
| `_id` | string (id) | no | Id of the sub-calendar of interest. This is the value used in a rule's `subcalendar_of_interest`, and the `source_id` of the matching sub-calendar in the users' calendar lists. |
| `name` | string | yes | Name of the sub-calendar. Required when creating one. HTML is sanitized. |
| `color` | string | yes | Display color (hex, for example `"#f0d050"`). Optional; when absent a color is assigned automatically for display. |
| `createdAt` | string (ISO 8601 date) | no | Creation date. |
| `updatedAt` | string (ISO 8601 date) | no | Last modification date. |

### The Rule object

| Field | Type | Writable | Description |
| --- | --- | --- | --- |
| `_id` | string (id) | no | Id of the rule. |
| `subcalendar_of_interest[]` | array of string (id) | yes | Sub-calendars of interest in which the occurrences of the rule appear. All must belong to the calendar of interest of the request. Defaults to **all** the sub-calendars of the calendar. |
| `name` | string | yes | Title of the generated calendar entries (for example `"Christmas Day"`). HTML is sanitized. |
| `kind` | string | yes | How occurrences are computed. One of `fixed`, `nth_weekday`, `last_weekday`, `direct_range`, `unique`. See [Rule kinds](#rule-kinds). A rule without `kind` is accepted but generates nothing. |
| `start` | string (ISO 8601 date-time) | yes | Required. Reference start. Its meaning depends on `kind` (see below). Interpreted in UTC. |
| `end` | string (ISO 8601 date-time) | yes | Required. Reference end. `end - start` is the duration of every occurrence. If `end` is not after `start`, the duration is 24 hours for an all-day rule and 1 hour otherwise. |
| `all_day` | boolean | yes | Default `true`. When `true`, occurrences are all-day entries (dates without time, taken from the UTC day of the computed start and end; the end day is exclusive). When `false`, occurrences are timed entries. |
| `month` | integer `1`-`12` | yes | Month of the occurrence (`1` = January). Required for `nth_weekday` and `last_weekday`. Optional for `fixed` and `direct_range` (overrides the month of `start`). Not used by `unique`. |
| `weekday` | integer `0`-`6` | yes | Day of the week (`0` = Sunday, `1` = Monday, `2` = Tuesday, `3` = Wednesday, `4` = Thursday, `5` = Friday, `6` = Saturday). Required for `nth_weekday` and `last_weekday`; not used by the other kinds. |
| `nth` | integer `1`-`5` | yes | Rank of the weekday in the month (`1` = first, `4` = fourth). Required for `nth_weekday`; not used by the other kinds. |
| `observance_policy` | string | yes | `none` or `nearest_weekday`. With `nearest_weekday`, an occurrence starting on a Saturday is moved to the Friday before and one starting on a Sunday to the Monday after (the "observed" day). With `none` or when absent, no shift. Not applied to `unique` rules. |
| `createdAt` | string (ISO 8601 date) | no | Creation date. |
| `updatedAt` | string (ISO 8601 date) | no | Last modification date. |

Responses may contain additional fields not listed here; they are internal, may change without notice and must not be relied upon.

### Rule kinds

All computations are done in UTC. The time of day of every occurrence is the UTC time of day of `start`.

| `kind` | Business meaning | Fields used | How each occurrence is computed |
| --- | --- | --- | --- |
| `fixed` | Same date every year ("December 25"). | `start`, `end`, optional `month` | One occurrence per year, on the day of the month of `start`, in `month` when given, otherwise in the month of `start`. If that day does not exist in the month for a given year (February 29), the last day of the month is used. |
| `nth_weekday` | Nth given weekday of a month, every year ("4th Thursday of November"). | `month`, `weekday`, `nth`, `start` (time of day), `end` (duration) | One occurrence per year, on the `nth` `weekday` of `month`. With `nth: 5` in a year where the month has only four such weekdays, the occurrence falls one week after the fourth, in the following month; use `last_weekday` for "last ... of the month". |
| `last_weekday` | Last given weekday of a month, every year ("last Monday of May"). | `month`, `weekday`, `start` (time of day), `end` (duration) | One occurrence per year, on the last `weekday` of `month`. |
| `direct_range` | A period of several days repeated every year ("December 24 to January 1"). | `start`, `end`, optional `month` | Computed exactly like `fixed`: one occurrence per year starting on the day/month of `start` and lasting `end - start`. |
| `unique` | A one-off date or period that does not repeat ("August 3 to August 14, 2026"). | `start`, `end` | A single occurrence from `start` to `end`. `month`, `weekday`, `nth` and `observance_policy` are ignored. |

Occurrences are generated asynchronously, shortly after a rule is created or updated, and then kept topped up automatically for roughly the next ten years. Yearly rules are generated from January 1 of the earlier of (the year of `start`, last year). When a rule is updated, its occurrences from the beginning of the current year onwards are recomputed.

Two access levels apply to `:calendar_of_interest_id`:

- **Edit** (update, delete, all rule endpoints): the calendar must be owned by the key's organization. Otherwise `404`, including for public calendars owned by someone else.
- **Use** (all `add_to` endpoints): the calendar must be owned by the key's organization **or** be public. Otherwise `404`.

### List calendars of interest

`GET /v2/calendar-of-interests`

Returns every calendar of interest the organization can use: the ones it owns and the public ones. Each element has its sub-calendars expanded and its rules in `cal_event_rules`. No pagination, no filter.

**Key scope:** organization

**Path parameters**

None.

**Query parameters**

None.

**Request body**

None.

**Response**

`200` with a JSON array of [Calendar of interest objects](#the-calendar-of-interest-object) (empty array when there are none). `cal_event_rules` is always present (empty array when the calendar has no rule).

**Errors**

| Status | When |
| --- | --- |
| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped. |
| `500` | Unexpected error. |

**Key scope:** organization

**Path parameters**

None.

**Query parameters**

None.

**Request body**

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `name` | string | yes | - | Name of the calendar. |
| `subcalendar_of_interests` | array of object | no | `[]` | Sub-calendars to create. The camelCase spelling `subcalendarOfInterests` is accepted as an alias. |
| `subcalendar_of_interests[].name` | string | yes | - | Name of the sub-calendar. |
| `subcalendar_of_interests[].color` | string | no | none | Display color (hex). |

**Response**

`201` with the created [Calendar of interest object](#the-calendar-of-interest-object), sub-calendars expanded (with their new `_id`). `cal_event_rules` is not included.

**Errors**

| Status | When |
| --- | --- |

| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped. |
| `500` | Unexpected error. |

### Update a calendar of interest

`PUT /v2/calendar-of-interests/:calendar_of_interest_id`

Partial update of a calendar of interest owned by the organization: rename it and/or manage its sub-calendars.

How `subcalendar_of_interests` is applied when it is present and not empty:

- The array becomes the **complete new list** of sub-calendars of the calendar.
- An element that is a string id, or an object with an `_id`, designates an existing sub-calendar, which is kept. It must already belong to this calendar, otherwise the whole request is rejected with `400`. An object with `_id` may also carry `name` and/or `color` to modify that sub-calendar.
- An element that is an object without `_id` creates a new sub-calendar (`name` required).
- An existing sub-calendar that is absent from the array is detached from the calendar. Always send the full list.
- An absent or empty array leaves the sub-calendars unchanged (it is not possible to remove all sub-calendars with this endpoint).

The new name is propagated to a user's calendar list the next time the calendar is added to that user (the `add_to` endpoints can be called again for this purpose). New sub-calendars appear in the users' calendar lists at their next calendar list refresh.

**Key scope:** organization

**Path parameters**

| Name | Type | Description |
| --- | --- | --- |
| `calendar_of_interest_id` | string (id) | Id of a calendar of interest owned by the organization. |

**Query parameters**

None.

**Request body**

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `name` | string | no | unchanged | New name of the calendar. |
| `subcalendar_of_interests` | array of (string id or object) | no | unchanged | Complete new list of sub-calendars, see above. The camelCase spelling `subcalendarOfInterests` is accepted as an alias. |
| `subcalendar_of_interests[]._id` | string (id) | no | - | Id of an existing sub-calendar of this calendar to keep / modify. Omit to create a new sub-calendar. |
| `subcalendar_of_interests[].name` | string | yes when `_id` is absent | unchanged | Name of the sub-calendar. |
| `subcalendar_of_interests[].color` | string | no | unchanged | Display color (hex). |

**Response**

`200` with the updated [Calendar of interest object](#the-calendar-of-interest-object), sub-calendars expanded. `cal_event_rules` is not included.

**Errors**

| Status | When |
| --- | --- |
| `400` | A referenced sub-calendar does not belong to this calendar, a new sub-calendar has no `name`, or a value is invalid. |
| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped. |
| `404` | No calendar of interest with this id is owned by the organization. |
| `500` | Unexpected error, including a malformed `calendar_of_interest_id`. |

### Delete a calendar of interest

`DELETE /v2/calendar-of-interests/:calendar_of_interest_id`

Permanently deletes a calendar of interest owned by the organization. Cascade:

- all its rules and all the calendar entries generated from them are deleted;
- all its sub-calendars are deleted;
- the calendar is removed from the calendar list of **every** user it had been added to, so its entries stop blocking their availability;
- it is removed from the user templates that referenced it.

This cannot be undone.

**Key scope:** organization

**Path parameters**

| Name | Type | Description |
| --- | --- | --- |
| `calendar_of_interest_id` | string (id) | Id of a calendar of interest owned by the organization. |

**Query parameters**

None.

**Request body**

None.

**Response**

`204` with an empty body.

**Errors**

| Status | When |
| --- | --- |
| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped. |
| `404` | No calendar of interest with this id is owned by the organization. |
| `500` | Unexpected error, including a malformed `calendar_of_interest_id`. |

**Example**

```bash
curl --request DELETE 'https://api.vyte.in/v2/calendar-of-interests/5f1e9b2a8c4d3e0012345a01' \
  --header 'Authorization: YOUR_API_KEY'
```

Response: `204` (empty body)

### Create a rule

`POST /v2/calendar-of-interests/:calendar_of_interest_id/rules`

Adds a rule to a calendar of interest owned by the organization. The occurrences of the rule are generated in the background right after the call; they are not part of the response and may take a moment to be visible to users.

The calendar must have at least one sub-calendar, otherwise the answer is `400`.

**Key scope:** organization

**Path parameters**

| Name | Type | Description |
| --- | --- | --- |
| `calendar_of_interest_id` | string (id) | Id of a calendar of interest owned by the organization. |

**Query parameters**

None.

**Request body**

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `subcalendar_of_interest` | array of string (id), or a single string (id) | no | all the sub-calendars of the calendar | Sub-calendars in which the occurrences appear. Every id must belong to this calendar. The camelCase spelling `subcalendarOfInterest` is accepted as an alias. |
| `name` | string | no | none | Title of the generated entries. Recommended: without it entries have no title. |
| `kind` | string | yes (see note) | none | `fixed`, `nth_weekday`, `last_weekday`, `direct_range` or `unique`. See [Rule kinds](#rule-kinds). Any other value is rejected with `400`. If omitted the rule is stored but never generates any entry. |
| `start` | string (ISO 8601 date-time) | yes | - | Reference start (UTC). |
| `end` | string (ISO 8601 date-time) | yes | - | Reference end (UTC). |
| `all_day` | boolean | no | `true` | All-day entries (`true`) or timed entries (`false`). |
| `month` | integer `1`-`12` | yes for `nth_weekday`, `last_weekday` | none | Month of the occurrence. Optional override for `fixed` and `direct_range`. |
| `weekday` | integer `0`-`6` | yes for `nth_weekday`, `last_weekday` | none | Day of the week, `0` = Sunday ... `6` = Saturday. |
| `nth` | integer `1`-`5` | yes for `nth_weekday` | none | Rank of the weekday in the month. |
| `observance_policy` | string | no | none (no shift) | `none` or `nearest_weekday`. Any other value is rejected with `400`. |

**Response**

`201` with the created [Rule object](#the-rule-object).

**Errors**

| Status | When |
| --- | --- |
| `400` | The calendar has no sub-calendar; a `subcalendar_of_interest` id does not belong to the calendar; `start` or `end` is missing or not a date; a field required by the `kind` is missing; `kind` or `observance_policy` is not an allowed value; `month`, `weekday` or `nth` is out of range. |
| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped. |
| `404` | No calendar of interest with this id is owned by the organization. |
| `500` | Unexpected error, including a malformed `calendar_of_interest_id`. |

**Example**

Thanksgiving: 4th Thursday of November, all day.

```bash
curl --request POST 'https://api.vyte.in/v2/calendar-of-interests/5f1e9b2a8c4d3e0012345a01/rules' \
  --header 'Authorization: YOUR_API_KEY' \
  --header 'Content-Type: application/json' \
  --data '{
    "subcalendar_of_interest": ["5f1e9b2a8c4d3e0012345a02"],
    "name": "Thanksgiving",
    "kind": "nth_weekday",
    "month": 11,
    "weekday": 4,
    "nth": 4,
    "start": "2026-11-26T00:00:00.000Z",
    "end": "2026-11-27T00:00:00.000Z",
    "all_day": true
  }'
```

Response: `201`

```json
{
  "_id": "5f1e9b2a8c4d3e0012345a06",
  "subcalendar_of_interest": ["5f1e9b2a8c4d3e0012345a02"],
  "name": "Thanksgiving",
  "kind": "nth_weekday",
  "month": 11,
  "weekday": 4,
  "nth": 4,
  "start": "2026-11-26T00:00:00.000Z",
  "end": "2026-11-27T00:00:00.000Z",
  "all_day": true,
  "createdAt": "2026-04-02T09:10:00.000Z",
  "updatedAt": "2026-04-02T09:10:00.000Z"
}
```

Other typical bodies:

```json
{ "name": "Christmas Day", "kind": "fixed", "start": "2026-12-25T00:00:00.000Z", "end": "2026-12-26T00:00:00.000Z", "observance_policy": "nearest_weekday" }
```

```json
{ "name": "Memorial Day", "kind": "last_weekday", "month": 5, "weekday": 1, "start": "2026-05-25T00:00:00.000Z", "end": "2026-05-26T00:00:00.000Z" }
```

```json
{ "name": "Summer closing 2026", "kind": "unique", "start": "2026-08-03T00:00:00.000Z", "end": "2026-08-15T00:00:00.000Z" }
```

### Update a rule

`PUT /v2/calendar-of-interests/:calendar_of_interest_id/rules/:cal_event_rule_id`

Partial update of a rule of a calendar of interest owned by the organization. Fields present in the body replace the stored values; fields absent are left unchanged, **except `subcalendar_of_interest`**: when it is absent, the rule is re-attached to **all** the sub-calendars of the calendar. Always resend `subcalendar_of_interest` if the rule targets a subset.

The resulting rule is validated as a whole (same rules as at creation). Its occurrences from the beginning of the current year onwards are then regenerated in the background.

**Key scope:** organization

**Path parameters**

| Name | Type | Description |
| --- | --- | --- |
| `calendar_of_interest_id` | string (id) | Id of a calendar of interest owned by the organization. |
| `cal_event_rule_id` | string (id) | Id of a rule attached to a sub-calendar of this calendar. |

**Query parameters**

None.

**Request body**

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `subcalendar_of_interest` | array of string (id), or a single string (id) | no | all the sub-calendars of the calendar (not "unchanged") | Sub-calendars in which the occurrences appear. Alias: `subcalendarOfInterest`. |
| `name` | string | no | unchanged | Title of the generated entries. |
| `kind` | string | no | unchanged | `fixed`, `nth_weekday`, `last_weekday`, `direct_range` or `unique`. |
| `start` | string (ISO 8601 date-time) | no | unchanged | Reference start (UTC). Cannot be emptied. |
| `end` | string (ISO 8601 date-time) | no | unchanged | Reference end (UTC). Cannot be emptied. |
| `all_day` | boolean | no | unchanged | All-day or timed entries. |
| `month` | integer `1`-`12` | no | unchanged | Month of the occurrence. |
| `weekday` | integer `0`-`6` | no | unchanged | Day of the week, `0` = Sunday ... `6` = Saturday. |
| `nth` | integer `1`-`5` | no | unchanged | Rank of the weekday in the month. |
| `observance_policy` | string | no | unchanged | `none` or `nearest_weekday`. |

**Response**

`200` with the updated [Rule object](#the-rule-object).

**Errors**

| Status | When |
| --- | --- |
| `400` | Same validation failures as at creation. |
| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped. |
| `404` | No calendar of interest with this id is owned by the organization, or the rule does not belong to this calendar. |
| `500` | Unexpected error, including a malformed `calendar_of_interest_id` or `cal_event_rule_id`. |

**Example**

```bash
curl --request PUT 'https://api.vyte.in/v2/calendar-of-interests/5f1e9b2a8c4d3e0012345a01/rules/5f1e9b2a8c4d3e0012345a04' \
  --header 'Authorization: YOUR_API_KEY' \
  --header 'Content-Type: application/json' \
  --data '{
    "subcalendar_of_interest": ["5f1e9b2a8c4d3e0012345a02"],
    "name": "Christmas Day (observed)",
    "observance_policy": "nearest_weekday"
  }'
```

Response: `200`

```json
{
  "_id": "5f1e9b2a8c4d3e0012345a04",
  "subcalendar_of_interest": ["5f1e9b2a8c4d3e0012345a02"],
  "name": "Christmas Day (observed)",
  "kind": "fixed",
  "observance_policy": "nearest_weekday",
  "month": 12,
  "start": "2026-12-25T00:00:00.000Z",
  "end": "2026-12-26T00:00:00.000Z",
  "all_day": true,
  "createdAt": "2026-04-02T09:05:00.000Z",
  "updatedAt": "2026-04-03T10:15:00.000Z"
}
```

### Delete a rule

`DELETE /v2/calendar-of-interests/:calendar_of_interest_id/rules/:cal_event_rule_id`

Permanently deletes a rule of a calendar of interest owned by the organization, together with all the calendar entries generated from it (past and future). The corresponding dates immediately stop blocking the availability of the users.

**Key scope:** organization

**Path parameters**

| Name | Type | Description |
| --- | --- | --- |
| `calendar_of_interest_id` | string (id) | Id of a calendar of interest owned by the organization. |
| `cal_event_rule_id` | string (id) | Id of a rule attached to a sub-calendar of this calendar. |

**Query parameters**

None.

**Request body**

None.

**Response**

`204` with an empty body.

**Errors**

| Status | When |
| --- | --- |
| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped. |
| `404` | No calendar of interest with this id is owned by the organization, or the rule does not belong to this calendar. |
| `500` | Unexpected error, including a malformed id. |

**Example**

```bash
curl --request DELETE 'https://api.vyte.in/v2/calendar-of-interests/5f1e9b2a8c4d3e0012345a01/rules/5f1e9b2a8c4d3e0012345a04' \
  --header 'Authorization: YOUR_API_KEY'
```

Response: `204` (empty body)

### Add a calendar of interest to users

Three routes share the same behaviour and differ only by the population they target:

| Route | Population |
| --- | --- |
| `POST /v2/calendar-of-interests/:calendar_of_interest_id/add_to/org` | Every member of the key's organization. |
| `POST /v2/calendar-of-interests/:calendar_of_interest_id/add_to/team/:team_id` | Every member of the team `:team_id`, which must belong to the key's organization. |
| `POST /v2/calendar-of-interests/:calendar_of_interest_id/add_to/user/:user_id` | The user `:user_id`, who must be a member of the key's organization. |

**`GET` is an alias of `POST`** on each of these three paths: `GET .../add_to/org`, `GET .../add_to/team/:team_id` and `GET .../add_to/user/:user_id` perform exactly the same modification and return the same response as the `POST`. A `GET` on these paths is therefore **not** a read: it changes data. Prefer `POST`.

Effect, for each targeted user:

- A calendar with `source: "vyte_calendar_of_interest"` and `source_id` equal to the calendar of interest id is added to the user's [calendar list](/reference/calendars/) (the calendar list is created if the user has none).
- The operation is idempotent: if the user already has this calendar of interest, no duplicate is created; its name is simply brought up to date.
- The sub-calendars of interest show up in the user's calendar list at its next refresh (for example the next `GET /v2/users/:user_id/calendars`), each with `display: false` and `busy: false`. **Until `busy` is set to `true` on a sub-calendar, its entries do not block the user's availability.** Enable them with `PUT /v2/users/:user_id/calendars` (see [Calendars](/reference/calendars/#update-the-calendars-of-a-user)).

The population is evaluated at the time of the call: users who join the organization or the team later do not receive the calendar automatically; call the endpoint again.

The calendar of interest must be owned by the organization or be public.

**Key scope:** organization

**Path parameters**

| Name | Type | Description |
| --- | --- | --- |
| `calendar_of_interest_id` | string (id) | Id of a calendar of interest owned by the organization, or of a public one. |
| `team_id` | string (id) | `add_to/team` route only. Id of a team of the organization. |
| `user_id` | string (id) | `add_to/user` route only. Id of a member of the organization. |

**Query parameters**

None.

**Request body**

None (any body is ignored).

**Response**

`200` with the [Calendar of interest object](#the-calendar-of-interest-object). In this response `subcalendar_of_interests` is an array of ids (strings), not of objects, and `cal_event_rules` is not included.

**Errors**

| Status | When |
| --- | --- |
| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped; or (`add_to/team`) the team belongs to another organization; or (`add_to/user`) the user is not a member of the organization. |
| `404` | The calendar of interest does not exist or is neither owned by the organization nor public; or (`add_to/team`) the team does not exist; or (`add_to/user`) the user does not exist. |
| `500` | Unexpected error, including a malformed id. If the error happens while processing a population, some users may already have received the calendar; the call can be safely repeated. |

**Example**

```bash
curl --request POST 'https://api.vyte.in/v2/calendar-of-interests/5f1e9b2a8c4d3e0012345a01/add_to/team/5f1e9b2a8c4d3e0012345b01' \
  --header 'Authorization: YOUR_API_KEY'
```

Response: `200`

```json
{
  "_id": "5f1e9b2a8c4d3e0012345a01",
  "name": "Company holidays",
  "org": "5f1e9b2a8c4d3e0012345001",
  "public": false,
  "subcalendar_of_interests": [
    "5f1e9b2a8c4d3e0012345a02",
    "5f1e9b2a8c4d3e0012345a03"
  ],
  "createdAt": "2026-04-02T09:00:00.000Z",
  "updatedAt": "2026-04-02T09:00:00.000Z"
}
```

### Remove a calendar of interest from users

| Route | Population |
| --- | --- |
| `DELETE /v2/calendar-of-interests/:calendar_of_interest_id/add_to/org` | Every member of the key's organization. |
| `DELETE /v2/calendar-of-interests/:calendar_of_interest_id/add_to/team/:team_id` | Every member of the team `:team_id`, which must belong to the key's organization. |
| `DELETE /v2/calendar-of-interests/:calendar_of_interest_id/add_to/user/:user_id` | The user `:user_id`, who must be a member of the key's organization. |

Removes the calendar of interest from the calendar list of each targeted user: the calendar and its sub-calendars disappear from the list (their `display` / `busy` settings are lost) and its entries stop blocking the user's availability. The calendar of interest itself, its sub-calendars and its rules are **not** deleted, and other users keep it. Users who did not have the calendar are left untouched (idempotent).

**Key scope:** organization

**Path parameters**

| Name | Type | Description |
| --- | --- | --- |
| `calendar_of_interest_id` | string (id) | Id of a calendar of interest owned by the organization, or of a public one. |
| `team_id` | string (id) | `add_to/team` route only. Id of a team of the organization. |
| `user_id` | string (id) | `add_to/user` route only. Id of a member of the organization. |

**Query parameters**

None.

**Request body**

None.

**Response**

`204` with an empty body.

**Errors**

| Status | When |
| --- | --- |
| `401` | Missing, unknown or deactivated API key. |
| `403` | The key is not `organization` scoped; or (`add_to/team`) the team belongs to another organization; or (`add_to/user`) the user is not a member of the organization. |
| `404` | The calendar of interest does not exist or is neither owned by the organization nor public; or (`add_to/team`) the team does not exist; or (`add_to/user`) the user does not exist. |
| `500` | Unexpected error, including a malformed id. |

**Example**

```bash
curl --request DELETE 'https://api.vyte.in/v2/calendar-of-interests/5f1e9b2a8c4d3e0012345a01/add_to/user/5f1e9b2a8c4d3e0012345678' \
  --header 'Authorization: YOUR_API_KEY'
```

Response: `204` (empty body)

## Notes and caveats

- **Typical sequence.** (1) Create the calendar with at least one sub-calendar. (2) Create its rules. (3) Add it to the organization, a team or a user. (4) For each user, read the calendar list (`GET /v2/users/:user_id/calendars`) so the sub-calendars appear, then set `busy: true` (and `display: true` if wanted) on the relevant sub-calendars with `PUT /v2/users/:user_id/calendars`. Without step 4 the calendar is attached but has no effect on availability.
- **`GET` on `add_to` paths writes.** It is a strict alias of `POST`. Make sure crawlers, link previewers or caching layers never issue these GETs.
- **Timestamps are camelCase here**: `createdAt` / `updatedAt`.
- **Response shapes differ by endpoint.** List: sub-calendars as objects plus `cal_event_rules`. Create / update: sub-calendars as objects, no `cal_event_rules`. `add_to` (POST / GET): sub-calendars as ids, no `cal_event_rules`. To read the rules of a calendar, use the list endpoint (there is no endpoint returning a single calendar or a single rule).
- **Deletes return `204` with no body** (calendar, rule, and `add_to` removals).
- **Rule updates reset the sub-calendar targeting** to all sub-calendars when `subcalendar_of_interest` is omitted.
- **Sub-calendar list replacement.** In the calendar update, a non-empty `subcalendar_of_interests` replaces the whole list; omitted sub-calendars are detached. Rules that targeted only a detached sub-calendar are no longer listed nor editable through the calendar: delete or retarget such rules before detaching a sub-calendar.
- **Occurrence generation is asynchronous.** A `201` / `200` on a rule means the rule is stored, not that its entries are already visible. Allow a short delay before checking availability.
- **Everything is computed in UTC.** For all-day rules, send `start` at `00:00:00.000Z` of the first day and `end` at `00:00:00.000Z` of the day after the last day (exclusive end), as in the examples.
- **`start` and `end` are mandatory for every kind**, including `nth_weekday` and `last_weekday`, where only their time of day and their difference (duration) matter.
- **Weekday numbering starts on Sunday** (`0`), month numbering starts at `1`.
- **Membership is not tracked.** `add_to/org` and `add_to/team` act on the members at the time of the call. Removing a user from a team does not remove the calendar from that user.
- **Public calendars** owned by another organization are visible in the list and can be added to / removed from your users, but any attempt to edit them, delete them or manage their rules answers `404`.
- **Malformed ids answer `500`**, not `400` or `404`. Validate that ids are 24 hexadecimal characters before calling.
